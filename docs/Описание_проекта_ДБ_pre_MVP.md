# Описание проекта DB_project-pre_MVP

Документ описывает проект в формате артефактов системного аналитика (по шаблону стр. 11–32). Диаграммы и изображения из раздела «Дизайн» не включены; основной акцент — детальное описание функций и API фронтенда и бэкенда.

---

## 1. Требования

### 1.1 Пользовательские истории (User story)

1. Я, как администратор, хочу просматривать и редактировать список пользователей и ролей, чтобы управлять доступом в системе.
2. Я, как пользователь, хочу регистрироваться (создавать учётную запись с именем, фамилией, email, ролью), чтобы получить доступ к функционалу.
3. Я, как пользователь, хочу верифицировать учётную запись по коду, чтобы подтвердить регистрацию.
4. Я, как пользователь, хочу запрашивать код смены пароля на email и менять пароль по коду, чтобы восстановить доступ.
5. Я, как пользователь, хочу просматривать список продуктов и их количество, чтобы формировать заказы.
6. Я, как пользователь, хочу просматривать чертежи (blueprints) и их изображения, чтобы выбирать изделия.
7. Я, как пользователь, хочу создавать транзакции (оплата) и просматривать историю транзакций, чтобы отслеживать покупки.
8. Я, как пользователь, хочу отправлять обратную связь (feedback), чтобы сообщать о проблемах или предложениях.
9. Я, как пользователь, хочу привязывать паспортные данные и подтверждать их, чтобы проходить верификацию.
10. Система должна записывать логи действий пользователей (система, действие, ответ, время), чтобы обеспечивать аудит.

### 1.2 Функциональные требования (кратко)

- Система должна предоставлять CRUD по пользователям, ролям, продуктам, количеству продуктов, чертежам, транзакциям, обратной связи, подтверждению паспортных данных, паспортным данным и логам.
- Система должна поддерживать верификацию пользователя по коду, отправку кода смены пароля на email и смену пароля по коду.
- Система должна хранить изображения продуктов и чертежей (файлы) и отдавать их по запросу.
- Списки сущностей должны поддерживать пагинацию (skip, limit).
- Формат обмена данными — JSON; даты — в формате ISO-8601.

### 1.3 Нефункциональные требования (кратко)

- Backend: REST API на FastAPI, асинхронная работа с PostgreSQL и MongoDB (для файлов).
- Frontend: SPA на React (Vite), запросы к API через axios с базовым URL `/api` (проксирование на бэкенд).
- CORS разрешён для localhost:3000, localhost:5173 и соответствующих 127.0.0.1.
- Авторизация на фронтенде: токен в localStorage, заголовок `Authorization: Bearer <token>`.

## 2. Сценарии использования (Use cases)

### 2.1 Вход в систему (логин)

| Поле | Описание |
|------|----------|
| **Заголовок** | Вход в систему |
| **Участники** | Пользователь (покупатель/продавец/администратор) |
| **Предусловие** | Пользователь открыл приложение и перешёл на страницу входа (/login). В системе есть пользователь с введённым email. |
| **Триггер** | Пользователь нажимает кнопку «Войти» на форме логина |
| **Ожидаемый результат** | Пользователь считается авторизованным, данные пользователя сохраняются в store (Zustand), выполняется переход на главную (/) или при роли admin — возможность перейти в админ-панель |
| **Основной сценарий** | a) Пользователь вводит email и пароль в поля формы.<br>b) Нажимает «Войти».<br>c) Система ищет пользователя по email в списке, полученном через GET /users.<br>d) При совпадении email пользователь маппится в модель авторизации (apiUserToAuthUser), сохраняется в useAuthStore.<br>e) Создаётся запись лога (POST /logs: system=auth, action=login).<br>f) Выполняется переход на /. |
| **Альтернативный сценарий** | a) Если пользователь с таким email не найден — отображается сообщение «Пользователь с таким email не найден», переход не выполняется.<br>b) Если список пользователей ещё загружается — кнопка «Войти» недоступна (disabled), текст «Загрузка...». |

### 2.2 Регистрация пользователя

| Поле | Описание |
|------|----------|
| **Заголовок** | Регистрация пользователя |
| **Участники** | Гость (неавторизованный пользователь) |
| **Предусловие** | Пользователь открыл приложение и перешёл на страницу регистрации (/register) |
| **Триггер** | Пользователь заполняет форму и нажимает «Создать аккаунт» |
| **Ожидаемый результат** | В системе создан пользователь (POST /users), пользователь переходит к шагу «Подтверждение email»; после ввода кода — верификация (GET /users/{id}/verification), пользователь авторизован и перенаправлен на / |
| **Основной сценарий** | a) Пользователь вводит фамилию, имя, отчество (опц.), email, пароль (не менее 8 символов), выбирает роль «Покупатель» или «Продавец».<br>b) При роли «Продавец» отображаются поля паспорта (серия, номер, кем выдан, дата выдачи) — обязательные для ввода.<br>c) Нажимает «Создать аккаунт».<br>d) Система отправляет POST /users с введёнными данными (role_id: 1 — buyer, 2 — seller).<br>e) Отображается экран «Подтверждение email» с полем для 6-значного кода.<br>f) Пользователь вводит код из письма и нажимает «Подтвердить».<br>g) Система вызывает GET /users/{id}/verification?verification_code=…<br>h) При успехе пользователь сохраняется в store, создаётся лог (action=register), переход на /. |
| **Альтернативный сценарий** | a) Если запрос POST /users завершился ошибкой — отображается formError (текст ошибки).<br>b) Если код не 6-значный — сообщение «Введите 6-значный код».<br>c) Если верификация не прошла — сообщение «Неверный код или код истёк».<br>d) Кнопка «Отправить повторно» — таймер 60 с (повторная отправка кода в текущей реализации не реализована через API). |

| **Альтернативный сценарий** | a) Если товар «Нет в наличии» — кнопка «В корзину» недоступна (disabled).<br>b) При ошибке загрузки каталога/товара отображается ErrorMessage и ссылка «В каталог».<br>c) При загрузке отображается LoadingSpinner. |

## 3. Реализация для Frontend

### 3.1 Точки входа

- Переход с экрана логина после успешной авторизации.
- Прямой переход по маршрутам приложения (в т.ч. `/admin` для админ-панели).
- Базовый URL API для всех запросов: `/api` (прокси на бэкенд, см. vite.config).

### 3.2 Переходы по экранам

- Логин → главная / админ (при роли admin).
- Админ-панель: ресурсы «Пользователи» (users) и «Роли» (roles) — список, просмотр, редактирование через react-admin (ListGuesser, ShowGuesser, EditGuesser).
- Доступ к админ-панели только при `user.role === 'admin'`; иначе редирект на главную.

### 3.3 Описание UI

Общее: экраны используют шрифт Unbounded, скругления (rounded-2xl, rounded-xl), тёмная палитра (чёрный/серый) для кнопок и акцентов. Фон приложения — анимированный (BackgroundAnimation); страницы логина и регистрации — сетчатый градиентный фон. Состояния загрузки — LoadingSpinner, ошибки — ErrorMessage.

### 4.3 API бэкенда (детальное описание методов)

Общие правила: REST, JSON; списки поддерживают пагинацию через query-параметры `skip` и `limit`; при ошибках клиента — 400/404, при ошибке приложения — 500; несуществующие ресурсы — 404. Datetime в ответах — строка ISO-8601 (например `"2025-02-20T12:00:00.000000"`).

#### 4.3.1 Пользователи — `/users`

**POST /users**

- Назначение: создание пользователя.
- Тело (Body): first_name, last_name, father_name (опц.), email, role_id, hash_password (опц.).
- Ответ: 200, тело — объект пользователя (UserResponse: id, first_name, last_name, father_name, email, is_acive, role_id, role_name, created_at, updated_at).

**GET /users**

- Назначение: список пользователей с пагинацией.
- Параметры (Query): skip (int, ≥0), limit (int, 1–1000).
- Ответ: 200, массив UserResponse.

**GET /users/{user_id}**

- Назначение: пользователь по ID.
- Параметры (Path): user_id (int).
- Ответ: 200 — UserResponse; 404 — пользователь не найден.

**PATCH /users/{user_id}**

- Назначение: обновление пользователя.
- Параметры (Path): user_id. Тело (Body): частичное обновление (first_name, last_name, father_name, email, hash_password, role_id, is_acive — все опционально).
- Ответ: 200 — UserResponse; 404 — пользователь не найден.

**DELETE /users/{user_id}**

- Назначение: удаление пользователя.
- Параметры (Path): user_id.
- Ответ: 200 — `{"ok": true}`; 404 — пользователь не найден.

**GET /users/{user_id}/verification**

- Назначение: верификация пользователя по коду.
- Параметры: user_id (Path), verification_code (Query, int).
- Ответ: 200 — успех; 400 — неверный код или истёк.

**POST /users/{user_id}/password/send-code**

- Назначение: отправка кода смены пароля на email.
- Тело (Body, опц.): current_password.
- Ответ: 200 — сообщение об отправке кода.

**POST /users/{user_id}/password/change**

- Назначение: смена пароля по коду из письма.
- Тело (Body): code (int, 6 знаков), new_password (str, 8–255).
- Ответ: 200 — успех.
